# Статус сущности: словарь в базе, значение вычисляемое

Четвёртый промпт, поверх `HARNESS-PLAN.md`, `-2` и `-3`. Составлен 2026-09-07, числа замерены
в этот день.

Причина простая: **между «не начата» и «закрыта» у задачи нет ничего**, и потому прогресс
может быть только «44 %» шагами по 1/227. Задача, у которой прошёл предполёт, написаны
падающие проверки и наполовину сделан код, в базе неотличима от той, которую никто не
открывал.

## Изменение 1. Словарь статусов — таблица, а не `CHECK`

«Какие статусы бывают у задачи» должно отвечаться запросом. Пока набор зашит в ограничение
DDL, веб-интерфейс зашьёт конвейер у себя, и две копии разойдутся молча — ровно как разошлись
`red-task` в раскладке, `red` в проекции и `test` в запросе гейта (см. изменение 5).

```sql
CREATE TABLE kind_status (
  kind     text NOT NULL,          -- task · decision · question · risk
  ord      integer NOT NULL,       -- место в конвейере
  name     text NOT NULL,
  title    text NOT NULL DEFAULT '',
  fact     text NOT NULL DEFAULT '',  -- ЗАПРОС: достигнут ли этот статус
  terminal boolean NOT NULL DEFAULT false,
  PRIMARY KEY (kind, name));
```

**Статус без факта — `unknown`, и никогда «достигнут».** Тот же закон, что у пункта гейта, у
пункта готовности и у ступени лестницы. Четвёртый раз одна форма: предмет, способ, вердикт —
и исполнитель у неё **один и тот же**, тот, что уже введён третьим промптом.

**Статус — либо константа из объявленного закрытого набора, либо булево. Свободного текста в
статусе не бывает.** Слова документа не пропадают: они идут в `state_text` рядом с константой,
и расхождение между словами и константой ловится. Что это правило чинит прямо сейчас — ниже,
в изменении 4: у решения статус объявлен двумя написаниями, на двух языках и значениями вида
«Принято, дополнено».

## Изменение 2. Конвейер задачи

Заказанный владельцем: **записана · проанализирована · проверена · в работе ·
имплементирована · закрыта**. Каждому — факт, а не пометка:

| статус | факт, которым он достигнут | есть ли факт сегодня |
|---|---|---|
| записана | сущность задачи существует | **да** |
| проанализирована | вердикт предполёта на текущей ревизии задачи | таблица есть, строк 0 |
| проверена | красная задача этой задачи закрыта | **да** — 82 закрытых |
| в работе | ветка задачи заведена, закрывающего трейлера нет | нет |
| имплементирована | проверки задачи зелёные на её коммите | нет |
| закрыта | трейлер `Task: <id> closed` | **да** — 99 |

Три из шести вычислимы сразу. Три требуют, чтобы харнес начал **записывать то, что и так
знает**: он запускает предполёт, он заводит worktree, он гоняет проверки. Подача — как
`task-state-push`: харнес подаёт, база принимает. Ничего нового изобретать не нужно.

## Изменение 3. Значение — представление, а не колонка

Владелец просил «отдельное поле в базе». Разложить это надо на две части, и обе — строки:

- **словарь** — таблица `kind_status`: настоящая вещь, её можно спросить и отрисовать;
- **факт** — строка в своей таблице: вердикт предполёта, трейлер, запись о прогоне проверок;
- **значение статуса** — `task_status`, **представление**.

Колонкой значение быть не может по той же причине, по какой ею не стал `is_ready`: задача
становится «проверенной» оттого, что закрылась её красная задача, и никто не пойдёт
переписывать ей колонку. Ничего при этом не прячется в прозе — под каждым статусом лежит
строка, которую видно.

**Достигнутый статус считается по каждому независимо**, а «текущий» — самый дальний из
подряд достигнутых. Разрыв в середине не проглатывается, а называется: задача
**имплементирована, но не проанализирована** — это работа, прошедшая мимо предполёта, и
сегодня такую нельзя ни найти, ни посчитать. Отдельный запрос `status_anomaly`.

Плюс `state_text` у задачи — как у вопроса, решения, риска и гейта: флаг для машины, слова
документа для человека, расхождение между ними ловится.

## Изменение 4. Статусы остальных видов — сплошная проверка

Прогнана по всем 38 видам: где статус объявлен в документе, где он спроецирован в колонку,
где его нет вовсе.

| вид | что есть сегодня | что делать |
|---|---|---|
| вопрос | `state`: open · decided · closed — константа | оставить; разобраться с `has_answer` (изменение 6) |
| риск | `state`: open · accepted · closed — константа | оставить |
| пункт гейта | `state`: unknown · passed · failed · refused | оставить |
| требование | `satisfied` булево + `priority` | оставить; жизненного цикла у требования нет и не нужен |
| история | `phase` — фаза пути, 188 из 188 | оставить |
| прогон | `left_open` булево | оставить |
| **решение** | `status`: accepted · superseded · **template** | привести к четырём, `template` убрать — ниже |
| **задача** | `state`: 3 константы, используются 2 | конвейер, изменение 2 |
| **проверка** | **статуса нет вовсе** | завести — ниже |
| **термин** | **статуса нет вовсе** | завести `retired` — ниже |
| **экран** | **статуса нет вовсе** | завести — ниже |
| потребность · фича · статья | статуса нет | не заводить: конвейера у них нет. Объявить это в плане, а не оставить умолчанием |

### Решение: четыре константы, и статус берётся из поля, а не из каталога

Расширить до `proposed · accepted · superseded · declined`. `template` из набора **убрать**:
`0000-template.md` — форма записи, а не решение в состоянии «шаблон»; статусом он попадает в
знаменатель.

Сегодня статус берётся из каталога жизненного цикла, и это работало, пока каталоги были. В
наборе сущностей каталога нет, и единственным источником становится поле документа — а оно
**не нормализовано**:

```
«Статус»  149 документов, значения: «Принято» ×146, «Принято, дополнено»,
                                    «Отменено ADR-0087 — откат убран из…», «принято 2026-09-05»
«Status»   23 документа,  значения: «Accepted» ×17, «Accepted for uber/fx + lifecycle; …»,
                                    «Accepted — but its package LAYOUT …», «Superseded by ADR-0014 — …»
```

Два написания, два языка, свободный текст. Разбор обязан свести это к четырём константам, а
всё, что стояло после константы, положить в `state_text` — там оно и нужно человеку.

### Проверка: у неё нет состояния, и потому `G3` нечем закрыть

Таблица проверок — `| ID | ← требование | Дано → Когда → Тогда |`. Колонки состояния нет ни в
документе, ни в `project_checks`. Значит вопрос «какие проверки написаны и наблюдались
падающими» — то, чем определяется красная фаза и что спрашивает `G3`, — не отвечается в
принципе.

Статус проверки выводится из фактов репозитория, не из документа:

| статус | факт |
|---|---|
| объявлена | строка в таблице проверок есть |
| написана | тест с этим именем есть в дереве кода |
| наблюдалась падающей | зафиксирован прогон, где она красная, до кода |
| зелёная | зафиксирован прогон, где она зелёная, на коммите задачи |

Первый вычислим сегодня. Остальные три требуют, чтобы харнес записывал прогоны, — тот же
разговор, что про предполёт в изменении 2, и та же подача.

### Термин: снят или живой

`project_terms` держит 42 термина без признака. Снятые названы **прозой внутри `Article 12`**:
`Incident`, `Alert`-как-процесс, `AlertState`, `SituationState.merged`, `watchdog`,
`data_source` — шесть. Правило `docs-lint` «вернувшихся терминов» держит этот список у себя.

Завести `retired` булевым, а снявшее решение — ссылкой. Тогда «какие термины сняты»
отвечается запросом, правило перестаёт носить копию списка, и «снятый термин вернулся»
становится соединением.

### Экран: состояния нет, и это уже названо дырой

`project_screens` — `id · title · area`, ничего больше. При этом карта проекта (§4sexies)
описывает целый слот документов **без раздела «Состояния»**: одиннадцать документов
`settings/`, оболочка, подробность тренда, три документа `inventory/`, два `configure/` — и
предупреждает, что список неполон, «проверять надо по отсутствию заголовка, а не по списку».

Завести у экрана два разных признака, и не смешивать их:

- `has_states` — булево: есть ли у документа раздел «Состояния». Это и есть та проверка по
  отсутствию заголовка, которую карта просит;
- `state` — константа жизненного цикла экрана, если владелец его объявит. Не объявлен —
  не заводить: пустой конвейер хуже отсутствующего.

`SCR-INV-05`, который сейчас роняет пункт `G2` «у экрана есть история или задача», — из этого
же слота.

## Изменение 5. `draft` — булево у каждой сущности

Чтобы документы готовились **параллельно исполнению**: набор v2 пишется, пока v1 делают, и
ничто из недописанного не попадает ни в гейт, ни в задачу, ни в знаменатель.

```sql
ALTER TABLE <каждая таблица сущностей> ADD COLUMN draft boolean NOT NULL DEFAULT false;
```

Это **факт авторства**, а не вывод: автор объявляет, что вещь ещё не в силе. Поэтому колонка,
а не представление — в отличие от статуса из изменения 3.

**Оговорка про имя.** В наборе `draft` уже занято: глоссарий определяет «Черновик · `draft`»
как несмёрженную версию конфигурации — это термин **продукта**. Колонки с таким именем в схеме
нет, а `ADR-0152` сузил `Article 12` до имён доменной модели, поэтому слой набора это имя взять
может. Названо здесь, чтобы никто не открыл столкновение заново и не переименовал полдороги.

### Пять правил, без которых флаг вреден

**1. Умолчание — `false`, и каждый читатель объявляет позицию.** Завести колонку и не тронуть
запросы — худший исход: черновик станет полноправным молча, и это хуже, чем его отсутствие.
Гейты, `next-task`, покрытие, все знаменатели читают **только непроект**; ручки, читающие
обе стороны, перечисляются поимённо.

**2. Черновик не идёт в знаменатель.** Тот же закон, что у `unknown`: отдельное число, никогда
не сложенное. Плитка показывает «принято N · черновиков M», и появление двадцати черновых
требований не двигает «покрыто 91 %» ни на пункт.

**3. Принятое не может ссылаться на черновик.** Это правило и делает параллельную подготовку
безопасной. Принятая задача, ссылающаяся на черновое требование, построена на несогласованном —
и сегодня это ничем не ловится. Проверка двусторонняя и несимметричная:

```
принятое → черновик    нарушение, называется поимённо
черновик → принятое    норма, молчит
черновик → черновик    норма
```

**4. Гейт читает только непроект.** Иначе подготовка v2 красит `G1` в красный по v1, и работа
встаёт из-за того, что кто-то начал писать следующую версию.

**5. Флаг объявлен в документе, а не только в базе.** Иначе база несёт факт, которого документ
не говорит, и они разъезжаются. Документной сущности — поле в шапке; внутренней — пометка в
строке.

### Позиция каждого читателя — таблицей, а не по памяти

Правило 1 требует, чтобы позицию объявил каждый. Вот все, кто читает сущности сегодня;
безымянного читателя не осталось.

**Три позиции, и только три:** `in-force` — черновики не видит вовсе · `both` — видит обе
стороны и **помечает каждую** · `drafts` — только черновики.

| ручка · представление | позиция | почему |
|---|---|---|
| `<вид>`, `<вид>-list`, `section`, `sections` | both | ими и готовят документы |
| `search` | both | ищут именно то, что пишут |
| `backlinks` | both, с пометкой | на ней держится правило «принятое не ссылается на черновик» |
| `put`, `put-section`, `rm` | both | запись черновика — обычная запись |
| `kinds` | both, двумя числами | «requirement 304, черновиков 12», а не 316 |
| `plan`, `kinds-due` | both | план знает и о том, что готовится |
| `next-task`, `blockers`, `preflight-queue` | **in-force** | задача не берётся по несогласованному |
| `requirements-of`, `tasks-of` | **in-force** | то же: исполнение |
| `gate`, `readiness`, `state-disagreements` | **in-force** | иначе подготовка v2 красит гейт v1 |
| `claims` | **in-force** | заявленное число считает действующий набор |
| `next-step` | **in-force** | лестница ведёт исполнение |
| `exceptions` | **in-force** | исключение из правила касается действующего |
| `progress` | both, **раздельно** | правило 2: «принято N · черновиков M», никогда суммой |
| `task_ready`, `requirement_covered` | **in-force** | вывод о готовности — про действующее |
| `events`, `process-history`, `measurements`, `norm-versions` | both | летопись не судит, а помнит |

**Проверки, обходящие набор целиком, — тот же вопрос и самый важный.** Их в таблице выше нет,
а именно они решают, получится ли готовить документы параллельно: полудописанный документ v2
входит во все правила разом и красит гейт, из-за которого встанет работа по v1. Оба обхода —
одноточечные, и фильтр ставится ровно там:

```
myack/.harness/scripts/docs-lint.mjs:113    const docs = [...documents(), ...prose()]
.harness/core/checks/documents:89           function walk(root, dir = root, out = [])
```

Позиция обоих — **in-force**: черновик не участвует ни в одном правиле, несущем гейт. Отсюда
же следует, почему правило 5 обязательно: `docs-lint` читает волт, а не базу, и обязан узнать
черновик **из самого документа**. Флаг, живущий только в колонке, для него не существует.

Отдельным счётом — «черновиков столько-то, они не проверялись»: пропуск, о котором не сказано,
неотличим от забывчивости.

**Позиция вшита в ручку, а не в параметр.** Соблазн — завести `includeDrafts` и оставить выбор
зовущему. Не делать: параметр, который надо помнить, — это параметр, который забудут, и забудут
именно в `next-task`, где цена ошибки наибольшая. Ручки исполнения не видят черновиков **по
устройству**; ручки подготовки видят обе стороны и всегда говорят, где какая. Тогда правило
владельца — «готовим документы — с черновиками, исполняем задачи — без» — выполняется само
тем, какими ручками агент пользуется, и не зависит от того, вспомнил он про флаг или нет.

Исключение одно и явное: `<вид>-list` принимает `only: drafts` — «покажи, что я подготовил».
Оно ничего не решает и ни во что не считается.

### Целый документ и одна строка — разные случаи

Пометить черновиком **весь** документ просто. Но черновой бывает и одна строка внутри
принятого: новое `FR` дописано в `srs`, а сам `srs` в силе. Значит флаг живёт **у сущности**, а
не только у документа, и внутренняя сущность несёт свою пометку в строке. Пометка документа
не делает черновыми его строки — иначе добавление одного требования выведет из силы все 304.

### Как черновик записан в документе — форма задаётся здесь, а не выбирается по пути

Читателей у пометки двое и они разные: проекция кладёт её в колонку, а `docs-lint` читает волт
и колонки не видит вовсе. Если форму не задать, они выберут разные, и набор получит два ответа
на один вопрос.

Шапки в наборе двух видов, и пометка обязана читаться из обеих:

```
- **Черновик**: да          буллетами  — как у решения и вопроса
| **Черновик** | да |       таблицей   — как у задачи
```

Один образец на оба: `\*\*Черновик\*\*\s*[:|]\s*да`, и **только в шапке** — до первого `##`.
Ниже по тексту слово ничего не значит: документ, рассуждающий о черновиках, не становится
черновиком.

**Жирность в образце обязательна, и вот почему.** В наборе уже есть строки
`| Черновик | \`draft\` | несмёрженная версия конфигурации` (глоссарий) и `| черновик |
главное действие \`Опубликовать\`` (экран разбора). Это **термин продукта**, а не статус
документа. Образец без `**` поймает обе и объявит черновиками глоссарий и экран. Проверено:
с жирностью — ноль совпадений, без неё — два ложных.

**Внутренней сущности — столбец, а не пометка в ячейке.** Строке таблицы дописывается
**последний** столбец `Черновик` со значением `да` либо пустым. Последний — потому что номера
существующих столбцов тогда не сдвигаются, а на них завязаны и разбор, и полсотни правил
`docs-lint`. Столбец добавляется только тем таблицам, где построчный черновик нужен: `srs`,
`test-cases`. Пометка знаком внутри ячейки запрещена: её не видно глазом в диффе и она ломается
о `\|`.

### Что править и где

Работа идёт в двух деревьях, и оба названы:

```
undassa/mh/server-rs/src/       колонка, позиции ручек, представления
myack-dev/.harness/core/checks/documents:89      обход набора — фильтр здесь
myack-dev/myack/.harness/scripts/docs-lint.mjs:113   обход набора — фильтр здесь
```

**Ничего в myack сегодня черновиком не является, и помечать не надо.** Флаг приезжает пустым:
0 сущностей, 0 документов. Первый прогон обязан показать нули везде — если где-то не ноль,
образец поймал термин продукта, и это дефект образца, а не находка.

### `draft` против жизненного цикла и против версии

У решения `proposed` значит ровно то же. Держать оба, но **требовать согласия**: `proposed` ⇒
`draft = true`, и это проверка, а не обычай. `declined` и `superseded` черновиками **не**
являются — они решённые, просто не действующие.

`draft` и версия — **разные оси**, и путать их нельзя: `draft` говорит «ещё не согласовано»,
версия — «в какой выпуск попадёт». Документ v2 бывает согласованным и при этом не входящим
в v1.

## Изменение 7. Что это даёт интерфейсу

Плитка задач перестаёт быть одним числом и становится конвейером — сколько на каждом статусе,
плюс `unknown`. Правило третьего промпта остаётся в силе дословно: **статус, чей факт не
записывается, идёт в `unknown`, а не в «сделано»**. Поэтому на первом же прогоне плитка
покажет честную картину: 99 закрыто, 82 проверено, и «проанализировано / в работе /
имплементировано» — неизвестно, потому что этих фактов ещё никто не пишет.

Это и есть польза: сегодня та же неизвестность выглядит как «не начата».

## Приёмка

Каждую проверку сломать нарочно прежде, чем объявить работающей.

1. «Какие статусы бывают у задачи» отвечается запросом к `kind_status`, а не чтением DDL.
2. Статус без факта отвечает `unknown`. Число «статусов без факта» — запрос, и на старте оно
   равно трём.
3. `task_status` для закрытой задачи даёт «закрыта»; для задачи с закрытой красной — не ниже
   «проверена». Проверить на `M0-T1` и на любой из 82.
4. Задача, у которой есть трейлер закрытия и **нет** вердикта предполёта, попадает в
   `status_anomaly`, а не читается как прошедшая конвейер целиком.
5. Черновик решения со статусом `proposed` записывается и читается. До изменения запись
   отвергалась ограничением — показать оба прогона.
6. `template` не считается ни в одном знаменателе.
6bis. Ни один статус в базе не хранит свободный текст: у каждого набор значений объявлен, а
   слова документа лежат в `state_text`. Проверяется запросом «значения статуса вне
   объявленного набора» — он обязан давать пусто. У решений до разбора: из 172 значений
   **163 — ровно константа** (но на двух языках), **9 несут свободный текст**, например
   «Принято, дополнено», «Accepted — confirmed 2026-07-27 (Postgres-native…)», «Superseded by
   ADR-0014 — the package-by-technical-layer split below is…». Одно из девяти — перечень
   вариантов в шаблоне, и он в знаменатель не идёт вовсе.
6ter. «Какие термины сняты» отвечается запросом и даёт шесть. Правило `docs-lint` перестаёт
   носить список у себя и читает его из базы — иначе списков снова два.
6quater. «Какие экраны без раздела «Состояния»» отвечается запросом по отсутствию заголовка,
   а не по перечню из карты.

   один: проверка, срабатывающая в одну сторону, ничего не доказывает.
