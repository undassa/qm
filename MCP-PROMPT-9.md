# Промпт 9 · Чужое дерево, зашитый образец и дверь, которая называет не ту причину

Мерено на `tot-ade` 10 сентября 2026, вечер. Каждая находка проверена
командой, приведённой рядом.

**Сначала о моей ошибке в этом же файле.** Первая редакция промпта утверждала,
что одиночка с пустым именем не читается ни одной дверью, и приводила
`document-plan`, `brs`, `chronicle`, `data-model`, `generator` как жертвы.
Это неверно. Одиночки, у которых документ есть, читаются прекрасно:

    mh call srs          → content 70 640 знаков
    mh call register     → content 88 200
    mh call traceability → content  2 267

Перечисленные же пять — это виды, у которых документа **нет вовсе**; ровно
их и называет красный пункт `required-kind-written`. Я принял сообщение об
ошибке за причину и не проверил обратный случай. Из этого осталась настоящая
находка — она первая ниже, и она про само сообщение.

---

## 1. Дверь отвечает «нужно имя» там, где верный ответ — «такого документа нет»

    mh call chronicle-list   → {"count":1,"ids":["chronicle"]}
    mh call chronicle        → {"why":"виду chronicle нужно имя"}
    mh call chronicle id=chronicle
                             → {"why":"виду chronicle нужно имя"}

Документа `chronicle` в наборе нет — это говорит гейт `G1`, пункт «у
обязательного вида есть документ либо названа причина»: `chronicle`,
`data-model`, `document-plan`, `risks`, `strs`, `test-cases`.

Две двери врут по-разному:

- **`<вид>-list` сообщает `count: 1` и подставляет имя вида как идентификатор**
  для вида, у которого нет ни одного документа. Пустоты в ответе нет — есть
  выдуманная единица. Контроль: у `after` документ существует и зовётся
  `release`, список отдаёт `["release"]`, а не `["after"]`.
- **Читатель называет не ту причину.** «Виду нужно имя» отправляет искать имя,
  которого не существует. Верный ответ — «документа вида `chronicle` в наборе
  нет», и он же сразу говорит, что делать.

Цена измерима: я потратил на это полчаса и написал в этот файл неверную
находку, прежде чем проверил обратный случай.

## 2. `code-address-resolves` меряет наш репозиторий адресами чужого проекта

39 нарушений из 39 — из документов вида `reference`, ветка `tot-dev/…`:

    reference tot-dev/linked/lenta-sessiy — packages/core/src/api/agent.ts:93
    reference tot-dev/linked/lenta-sessiy — cmd/tot-desktop/src/main.rs:432
    reference tot-dev/linked/lenta-sessiy — routes/ai/ai.rs:98
    reference tot-dev/linked/lenta-sessiy — services/ws.ts:57

Ни `packages/`, ни `cmd/`, ни `routes/`, ни `services/` в этом репозитории нет
— на верхнем уровне здесь только `crates/`:

    ls -d */    → crates/

Это дерево соседнего продукта. Из 108 документов вида `reference` 107 имеют
имя вида `tot-dev/...`: чужой набор внесён сюда целиком как справочный
материал. Адрес внутри справки — адрес в дереве того, о чём справка.

**Правило при этом работает, и это проверено подсадкой, а не предположено.**
В наш документ `design-view:audit` вписана строка
`` `crates/tot-core/src/lib.rs:999999` ``; после `mh sense` пункт дал 40
вместо 39 и назвал причину точно:

    design-view audit — crates/tot-core/src/lib.rs:999999: в файле строк 581

Откат вернул 39, текст раздела совпал с исходным побайтно.

**Что просится.** Отбор в `project_code_address` не должен брать документы
вида `reference`. Отменять пункт нельзя: он ослепнет на 64 сходящихся
адресах, а подсадка показала, что видит он их хорошо.

## 3. `question-register-consistent` зашил `^Q-`, хотя словарь объявляет образец

Правило состоит из трёх ветвей. Первые две сходятся:

| | сказано в указателе | в наборе |
|---|---|---|
| открытых | 2 | 2 |
| закрытых | 69 | 69 |

Третья ветвь считает ячейки первого столбца условием

    c.value ~ '^Q-'

и получает ноль. Набор зовёт вопросы `OQ-79`, `OQ-80` — под `^Q-` они не
подходят. При этом словарь **уже** несёт нужный образец, и его причина
называет ровно это расхождение:

    role  = id.question
    value = ^OQ-[0-9]+$
    why   = этот набор зовёт вопросы OQ-nn; общий образец ^Q-\d+$ —
            форма соседнего

Роли `register.questions`, `register.open`, `register.closed` правило из
словаря читает. Образец строки — нет.

## Мелочи при дверях

**`coverage` не открывается своим читателем:**

    mh call coverage-list → {"count":1,"ids":["coverage"]}
    mh call coverage      → {"why":"вид и имя записаны в документе,
                                    а ключ запрещает второе"}

Документ существует — его читает правило `subsystem-coverage-matches`, — а
дверь к нему отказывает по причине, из которой не следует, что делать.

**`addresses-declared` не говорит, кто адрес назвал.** Отдаёт 103 строки вида
`{"path":"arch/build.rs","line":"198"}`. Гейт этот вопрос решает — в находках
стоит `reference tot-dev/linked/lenta-sessiy`, — а дверь его не отвечает,
поэтому отделить свои адреса от чужих через `mh` нельзя.

## 4. Двух связей объявить нечем: история ← требование, фича ← история

Два пункта `G1` красны по семнадцать раз каждый — это все истории набора:

    story-has-requirement    17 :: у истории есть требование или названная причина
    feature-matches-stories  17 :: фича и её истории сходятся

Случаи разные, и путать их не надо.

**История ← требование: набор это говорит, сервер читает не там.** Все
семнадцать историй несут строку вида

    **Требования:** UI-10 · UI-13 · UI-18 · UI-19 · UI-32 · UI-37 · FR-01 ·
    FR-02 · FR-03 · FR-07 · FR-09 · FR-10 · FR-12 · NFR-01 · NFR-02.

Измерено обходом всех семнадцати: `требования=ДА` у 17 из 17. При этом

    mh call links-of kind=story id=s1-understand-project
    → {"features":[],"needs":[],"requirements":[],"screens":[]}

Связь есть в документе и её нет в колонках.

**Фича ← история: набор не говорит этого нигде.** Обход всех пятидесяти фич
образцом `\bs\d+-[a-z0-9-]+\b` даёт **ноль**: ни одна фича не называет ни одной
истории. Обратная сторона тоже пуста — ни в одной истории нет строки `**Фича:**`
(измерено, 0 из 17). Здесь пункт красен по делу: связь не объявлена ни с одной
стороны.

**И ту, и другую объявить нечем.** В `mh tools` есть:

| дверь | что объявляет |
|---|---|
| `story-add` | имя, заголовок, область |
| `story-detail-add` | персона, экран |
| `feature-link-add` | фича → требование, фича → статья конституции |

Двери «история несёт требование» нет. Двери «фича несёт историю» нет.
Правило `feature-matches-stories` читает `project_feature_stories`,
`story-has-requirement` — `project_story_requirements`; заполнить их через
сервер нельзя ничем.

**Что просится — две двери, по образцу `feature-link-add`:**

    story-requirement-add   story=<история> requirement=<FR|UI|NFR> [drop]
    feature-story-add       feature=<фича>  story=<история>          [drop]

Тогда семнадцать строк, которые сегодня стоят в прозе, станут колонками — а
второй пункт получит способ быть закрытым правдой, а не отменой.

## Ещё раз про словарь

Словарь набора уже несёт образцы имён, и несёт их с причинами:

    id.story        ^s[0-9]+-[a-z0-9-]+$
    id.screen       ^[0-9]{2}-[a-z0-9-]+$
    id.task         ^[mv][0-9]+-t[0-9]+[a-z]?$
    id.question     ^OQ-[0-9]+$
    id.requirement  FR-[0-9]+

Правило `question-register-consistent` (находка 3) зашивает `^Q-` рядом с
объявленным `id.question`. Стоит проверить остальные разборы на то же: словарь
для того и заведён, чтобы форма имени была объявлена один раз, а не повторена
в каждом образце.
