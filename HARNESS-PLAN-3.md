# Процесс в базе: диспетчер шагов и честный прогресс

Третий промпт, поверх `HARNESS-PLAN.md` и `HARNESS-PLAN-2.md`. Составлен 2026-09-07, числа
замерены в этот день.

Цель одна: **процесс перестаёт быть прозой, которую исполняет читающий.** Сегодня агент
читает лестницу в `/godzy`, глазами прогоняет её ступени и сам решает, что запускать. Отсюда
две вещи, которых нет: диспетчер не может ошибиться воспроизводимо, и веб-интерфейс не может
показать, где мы.

---

## 1. Лестница переезжает в базу

В `/godzy` уже написано ровно то, что нужно, — 11 ступеней, у каждой **вопрос · чем
отвечается · кто чинит**. Переносить надо её, а не придумывать новую.

Две ступени сегодня не машинные вовсе: «открыть **каждый** адрес в `project.md`» и «`grep` по
`[TO BE DECIDED]` молчит». Остальные зовут команду, но вывод из ответа делает читающий.

Ключ — **набор**, а не проект, как у `harness_agent`: лестница принадлежит харнесу и одинакова
везде, где он привязан.

```sql
CREATE TABLE harness_process (
  set_name text NOT NULL, name text NOT NULL, title text NOT NULL DEFAULT '',
  PRIMARY KEY (set_name, name));

CREATE TABLE harness_process_step (
  set_name    text NOT NULL,
  process     text NOT NULL,
  ord         integer NOT NULL,        -- номер ступени
  question    text NOT NULL,           -- что спрашивает
  method_kind text NOT NULL CHECK (method_kind IN ('query','command','signed','unknown')),
  method      text NOT NULL DEFAULT '',
  when_query  text NOT NULL DEFAULT '',-- когда ступень вообще в игре; пусто = всегда
  owner_kind  text NOT NULL CHECK (owner_kind IN ('skill','agent','none')),
  owner       text NOT NULL DEFAULT '',
  touches     text NOT NULL CHECK (touches IN ('corpus','repository')),
  PRIMARY KEY (set_name, process, ord));
```

**Ступень без способа — `unknown`, и диспетчер на ней останавливается, называя её.** Не
«считаем пройденной». Перенести все 11 со способом `unknown` — и сразу появится число,
которого нет: сколько ступеней входа не отвечаются машиной. Так же сработало с пунктами
готовности.

**Условная ступень объявляется, а не подразумевается.** Ступень 3 меняет смысл ступеней 5 и 8:
в первой версии набор пишется впервые, во второй — считается дельта. Сегодня это абзац под
таблицей. `when_query` делает пропуск видимым: ступень **пропущена с причиной**, а не молча.

**Сторона объявляется.** Ступени 0–7 читают набор, 8–10 пишут в репозиторий. Это факт о
ступени: диспетчер обязан отказаться запускать репозиторную ступень, пока фаза набора открыта.

## 2. Скиллы — в базу, иначе `owner` не проверяем

Субагенты уже там: `harness_agent`, 7 в наборе `godzy`, с `push` / `status` / `sync`. Скиллов
в базе **нет**. Пока их нет, `owner='godzy-plan'` указывает на то, чего база не подтвердит, и
переименованный скилл ломает предложение, а не связь.

`harness_skill` тем же механизмом, той же формы: имя, описание, тело, хеш, кто и когда положил.
Тогда `owner` проверяется внешним ключом, а `.harness/doctor` считает расхождение установленного
с базой для скиллов ровно так, как уже считает для агентов.

## 3. Один исполнитель способов, три вызывающих

Пункт гейта, пункт готовности и ступень лестницы — **одна форма**: предмет, способ проверки,
вердикт. Мы её построили дважды. Третья реализация разойдётся с первыми двумя молча — как
разошлись две таблицы связей задача→требование, пока одну не удалили.

Поэтому: **одно место, которое умеет исполнить `query`, `command` и `signed` и вернуть
вердикт**, и три вызывающих — `gate`, `readiness`, `next-step`. Вердикт один и тот же:
`passed` · `failed` · `unknown` · `unsigned` · `stale`, плюс число нарушений и подробность.

## 4. Диспетчер

`next-step` — как `next-task`: идёт по ступеням процесса, исполняет способ, возвращает
**первую невыполненную вместе с владельцем**, и отказывается там, где способа нет.

```json
{
  "process": "godzy",
  "at": { "ord": 5, "question": "полон ли набор документов этой фазы",
          "state": "failed", "ownerKind": "skill", "owner": "godzy-docs",
          "touches": "corpus" },
  "passed": [0,1,2,3,4],
  "skipped": [{ "ord": 3, "why": "версия одна: дельты нет" }],
  "unanswerable": [{ "ord": 1, "why": "у ступени нет способа проверки" }]
}
```

Три списка, а не один. Пройденное, пропущенное **с причиной** и неотвечаемое — разные вещи, и
слипшись они дают ту самую зелень, которая ничего не мерит.

**Каждый проход записывается**, как `preflight_verdict`:

```sql
CREATE TABLE process_run (
  project_id text NOT NULL, process text NOT NULL, at bigint NOT NULL,
  ord integer NOT NULL, state text NOT NULL, detail text NOT NULL DEFAULT '',
  PRIMARY KEY (project_id, process, at, ord));
```

Тогда «почему диспетчер выбрал это» отвечается после, а ступень, которая скачет, видна.

## 5. Прогресс для веб-интерфейса — и почему процент бывает враньём

Замерено сегодня. Так выглядят плитки, если считать честно:

| плитка | сделано | открыто | не отвечается | что показывать |
|---|---|---|---|---|
| задачи | 99 | 128 | 0 | **44 %** |
| вопросы | 356 | 3 | 0 | **99 %** |
| требования покрыты | 276 | 28 | 0 | **91 %** |
| пункты гейтов | 10 | 2 | **6** | 83 % из отвечаемых, и треть не отвечается |
| пункты готовности | 0 | 1 | **1737** | **процента нет** |

Последняя строка — весь смысл этого раздела. Наивная формула «объявлено выполненным ÷ всего»
дала бы `22 / 1738 = 1,3 %`, и это враньё: 1737 пунктов невозможно проверить ничем. Полоска на
1 % так же неверна, как полоска на 100 %.

**Правило: всякая цифра прогресса — три числа, никогда одно.**

```
done      ответ получен и он «выполнено»
open      ответ получен и он «не выполнено»
unknown   ответить нечем — способа нет
```

Процент считается **от отвечаемого**: `done / (done + open)` — и **всегда** показывается рядом
с `unknown`. Плитка, у которой `done + open = 0`, показывает не «0 %», а «пока не измеряется» и
число `unknown`. Полоска, которая сложила `unknown` в любую из сторон, — тот же дефект, что
зелёный чек-лист, который ничего не мерит.

**Прогресс не хранится.** Он выводится представлениями, как `task_ready` и `requirement_covered`:
сохранённый процент протухает в тот момент, когда закрылась соседняя задача.

- `process_state` — лестница как 11 строк: ступень, вопрос, состояние, владелец, сторона.
  Это экран «где мы сейчас»;
- `corpus_progress` — плитки выше, по три числа на каждую;
- `phase_progress` — то же в разрезе фаз `P0…P5` и их гейтов `G0…G4`: гейты уже считаются и уже
  кладут объявленное рядом с вычисленным, эту пару и показывать.

**Движение — из журнала, а не из снимка.** `process_run` и история сущностей дают линию во
времени: интерфейс рисует её, а не хранит «было 40 %, стало 44 %».

**Что должно быть видно на экране, чтобы можно было работать**, а не только смотреть:

1. **где мы** — первая невыполненная ступень, её вопрос и владелец;
2. **что запустить** — имя скилла либо субагента из `owner`, проверяемое по базе;
3. **что мешает** — для задачи это уже отвечает `blockers`, для гейта `disagreeWithDeclared`;
4. **чего мы не знаем** — счётчик `unknown` на видном месте, а не в подвале. Это единственная
   плитка, которая должна расти в глазах, пока её не закроют.

## 6. `godzy-doctor-fix`: другая работа, а не отменённая

Скилл целиком про починку дерева: слоты, относительные ссылки, `%20`, переезды файлов. Дерева
нет — и переписывать его формулировками нечего, у него меняется предмет.

Что остаётся настоящей работой в наборе сущностей:

- ссылка, которая не разрешается, и сущность, на которую никто не ссылается, — один дефект с
  двух сторон, и вторую сторону уже отвечает `corpus backlinks`;
- проза, расходящаяся со ссылкой рядом: текст называет одну сущность, ссылка ведёт к другой;
- поле статуса, которому противоречит текст записи;
- заявленное число, разошедшееся с фактом, — `claims` уже находит одно такое (статей 15 против
  16).

Переписать скилл на эти четыре, и **не описывать в нём, чего больше нет**: правильные действия,
без истории отменённого.

## 7. Приёмка

Как всегда: каждую проверку сломать нарочно прежде, чем объявить работающей.

1. Лестница в базе, 11 ступеней. Число «ступеней без способа проверки» отвечается одним
   запросом и на старте не ноль.
2. `next-step` возвращает первую невыполненную ступень с владельцем и **тремя** списками:
   пройдено, пропущено с причиной, неотвечаемо.
3. Ступень с `owner_kind='skill'` и несуществующим именем **не заводится**: внешний ключ
   отказывает. Для этого скиллы сперва в базе.
4. Условная ступень 3 при одной версии отмечена пропущенной **с причиной**, а не пройденной.
5. Диспетчер отказывается запускать ступень с `touches='repository'`, пока открыта фаза набора,
   и называет причину.
6. Плитка «пункты готовности» показывает «пока не измеряется» и число 1737, а не «1,3 %».
7. Плитка «задачи» показывает 44 % и ноль в `unknown`.
8. Один и тот же `query` даёт один и тот же вердикт, вызванный через `gate`, `readiness` и
   `next-step`: исполнитель один.
9. `process_run` хранит проходы, и «ступень скачет» видно запросом.
