## Что уже стоит и переделывать не надо

- **риски нормализованы** в `project_risks`: влияние и вероятность из малых закрытых наборов,

## Изменение 1. Объявленное отсутствие хранится как отсутствие

Это самое важное и самое дешёвое в исправлении.

`M0-T12` в поле «Требования» говорит буквально:

> нет собственных; исполняет решения Q-277 и Q-282 (ADR-0150)

Разбор вытащил из этой фразы `Q-277` и `Q-282` и записал их **требованиями задачи**. Ручка
`next-task` сегодня отдаёт `M0-T12` с `requirements: 2` и `requirementText: "Q-277 · —"` —
то есть ровно противоположное тому, что написано в документе.

Это не единичный случай, это правило разбора:

```
задач, объявивших «нет собственных» в поле «Требования»      52
из них всё равно получили связи                              42
связей, порождённых этими фразами                            86
   из них не разрешаются в требование (видно, что мусор)      63
   из них разрешаются в настоящее требование (НЕ ВИДНО)       23
всего связей задача→требование                              371
всего висячих связей                                         72   (19%)
   task-id 63 · Q-id 8 · ADR-id 1
```

Двадцать три связи — самое опасное здесь. Они указывают на существующие требования, выглядят
как настоящие и не отличимы от настоящих ничем: `M0-T9` говорит «нет собственных; обслуживает
`FR-ORG-24` … требование принадлежит `M2-T29`», и `FR-ORG-24` уезжает в базу как требование
`M0-T9`. Любая ручка «открытые требования задачи» соврёт, и соврёт правдоподобно.

**Что делать.** Объявленное отсутствие — это факт, и у факта есть строка:

```sql
ALTER TABLE project_plan_tasks
  ADD COLUMN has_own_requirements boolean,          -- NULL = не объявлено вовсе
  ADD COLUMN requirements_note    text NOT NULL DEFAULT '';   -- фраза целиком, как написана
```

И правило разбора: **из объяснения отсутствия связи не добываются.** Фраза, начинающаяся с
«нет собственных», кладётся в `requirements_note` целиком, а идентификаторы в ней остаются
упоминаниями — им место в `project_document_links`, не в таблице связей. Это тот же различ
«объявлено против упомянуто», который уже принят для набора; здесь он просто не применён.

Три состояния, и все три разные: требований нет и это объявлено (52 задачи) · требования есть
· поле не заполнено вовсе. Третье — дефект документа, и ловить надо его.

## Изменение 2. Чек-лист становится строкой со способом проверки

**Замер.** Во всём наборе 1883 пункта вида `- [ ]` / `- [x]`:

```
задачи            1133   в 145 документах
красные задачи     492   в  82
order.md           145   доска волны
приёмка             37
document-plan       18   пункты гейтов
test-plan           11
вопросы Q-323…348   47   в 13
                  ─────
                  1883   отмечено 22
```

**Отмечено двадцать два из тысячи восьмисот восьмидесяти трёх, и одиннадцать из этих
двадцати двух — пункты гейтов в `document-plan.md`.** На все 145 задач приходится один
документ с отметками (`M2-T1`, три пункта), и та задача даже не закрыта. А **все 17 закрытых
задач не имеют ни одного отмеченного пункта готовности**.

`order.md` — отдельно: 145 пунктов, отмечено 0, и отмечено не будет никогда, потому что
`myack/.harness/scripts/order.mjs:85` пишет `- [ ]` безусловно при каждой пересборке доски. Доска, которая по
устройству не может позеленеть.

Вывод простой: галочка пишется один раз и больше не трогается. Вычислять её — не улучшение, а
единственный способ, чтобы она что-нибудь значила.

**Одна таблица на все виды, а не шесть.** Пункты одной формы: владелец, порядок, текст,
способ проверки. Различаются только владельцем. (Сравни с историей, где три вида имели РАЗНЫЕ
формы, — там три таблицы и были правы.)

```sql
CREATE TABLE readiness_item (
  project_id  text NOT NULL,
  owner_kind  text NOT NULL,   -- task · red-task · acceptance · gate · question · plan
  owner_id    text NOT NULL,
  ord         integer NOT NULL,
  text        text NOT NULL,   -- как написано
  declared    boolean,         -- стояла ли галочка в документе; NULL — пункт без галочки
  method_kind text NOT NULL CHECK (method_kind IN ('query','command','signed','unknown')),
  method      text NOT NULL DEFAULT '',
  PRIMARY KEY (project_id, owner_kind, owner_id, ord)
);
```

`declared` хранится рядом со способом ровно затем, зачем `gate` уже хранит объявленное рядом с
вычисленным: расхождение между «написано выполнено» и «проверено выполнено» — это и есть то,
ради чего всё считается.

**Правило, без которого затея вредна.** Состояние пункта вычисляется **только** когда пункт
объявил способ. Пункт со способом `unknown` остаётся `unknown` и никогда не становится `done`.
Выводить выполненность из прозы сопоставлением слов запрещено: зелёный чек-лист, который
ничего не мерит, хуже отсутствующего, потому что его читают и верят.

**Отсюда порядок работ.** Сначала перенести все 1883 пункта со способом `unknown`. Это ничего
не проверяет — и сразу даёт число, которого сегодня нет: сколько пунктов готовности не имеют
способа проверки. Дальше способ добывается по одному, и прогресс виден запросом.

Состояние — не колонка. См. изменение 3.

## Изменение 3. Факт хранится, вывод вычисляется

Соблазн — дописать в таблицы `is_ready`, `is_blocked`, `is_open`. **Не делать.** Сохранённый
вывод протухает в тот момент, когда меняется то, из чего он выведен: задача становится готовой
оттого, что закрылась соседняя, и никто не переписал ей колонку.

| Что | Это | Где живёт |
|---|---|---|
| `question.state` = closed | факт: так объявлено | колонка |
| `requirement.satisfied` | факт: пометка стоит | колонка |
| `task.has_own_requirements` | факт: так объявлено | колонка |
| `readiness_item.declared` | факт: галочка стояла | колонка |
| «задача готова к взятию» | вывод из зависимостей и фазы | **представление** |
| «требование покрыто» | вывод из проверок | **представление** |
| «пункт готовности выполнен» | вывод из способа | **представление** |

Назвать явно и держать рядом: `task_ready`, `requirement_covered`, `readiness_state`. Тогда
«почему задача не готова» — это `select`, а не рассуждение.

## Изменение 4. Исключение — строка, а не абзац

Историй 188, с требованием 184, без требования 4: `US-DET-01`, `US-FEED-04`, `US-FEED-08`,
`US-WHY-05`. Все четыре **объявлены законными** в `COVERAGE.md` §4 — история про
представление, её доказывает приёмка экрана.

Объявлены прозой. Значит всякая ручка, считающая дыры, не отличит исключение от дыры, не
прочитав документ, — и либо соврёт про четыре дыры, либо тихо спрячет настоящую пятую, когда
та появится.

```sql
CREATE TABLE rule_exception (
  project_id  text NOT NULL,
  rule        text NOT NULL,     -- «история без требования»
  entity_kind text NOT NULL,
  entity_id   text NOT NULL,
  reason      text NOT NULL,
  decided_by  text NOT NULL DEFAULT '',
  PRIMARY KEY (project_id, rule, entity_kind, entity_id)
);
```

Ручка, сообщающая дыры, возвращает **три** числа: дыр, исключений, и «исключение объявлено, а
дыры уже нет» — последнее значит, что исключение пора снять.

## Изменение 5. Заявленное число сверяется с фактом — но сначала говорит, что считает

`project_document_plan_counts` хранит числа, которые документ о себе заявляет. Рядом, в тех же
таблицах, лежит факт. Сравнения между ними нет. Сверка сегодня — человек прогоняет команду из
`document-plan.md` руками и вписывает число обратно прозой.

Что даёт сравнение прямо сейчас:

| заявлено | факт | |
|---|---|---|
| статей 15 | **16** | **протухло**: `Article 16` есть в конституции, число не поправили |
| решений 172 | 171 | законно: 172 — файлы вместе с шаблоном, 171 — записи |
| требований 272 | 304 | законно: 272 — это FR, а таблица держит FR+NFR (32) |
| потребностей 79 · проверок 360 · экранов 68 · NFR 32 | сходится | |

Одно настоящее расхождение, два ложных — и ложные ложны по одной причине: **строка не говорит,
что именно она считает.** Поэтому сверку нельзя завести в лоб: она даст два крика волком, им
перестанут верить, и `15` против `16` утонет ровно так, как утонуло сейчас.

Значит у заявленного числа появляется поле «над чем считано» — запрос либо команда, тот же
способ, что у пункта чек-листа. `172` считается по файлам, `272` — по `id NOT LIKE 'NFR-%'`.
Тогда сходится всё, кроме того, что действительно разошлось, и это становится пунктом гейта.

Замечу про `document-plan.md`: он **сам** примиряет 172 и 171 («разные корпуса, не
расхождение») и датирует замер. Я думал найти там небрежность и не нашёл — документ аккуратнее
своей проекции. Дефект не в том, что человек пишет числа плохо, а в том, что он вынужден их
писать: прошлый замер отстал на десять подписей и был исправлен вручную четырьмя днями позже.

## Изменение 6. Ручки, которых нет

Каждая отвечает одним вызовом и **называет, чего не знает**. Сбор ответа из нескольких вызовов
на стороне агента — место, где он ошибётся молча.

### `readiness(kind, id)`
Чек-лист сущности с вычисленным состоянием каждого пункта, честным `unknown` там, где способа
нет, и объявленным `declared` рядом. Сводка: выполнено · не выполнено · **не проверяемо** ·
**объявлено выполненным, но не проверяемо**.

### `requirements-of(task)` и `tasks-of(requirement)`
Обе стороны одной связи. У первой — состояние каждого требования: покрыто ли проверкой, стоит
ли `✓уд`, каким приоритетом; и **обязательно** `has_own_requirements` из изменения 1, чтобы
«нет собственных» доехало как ответ, а не как пустота. У второй — состояние каждой задачи.

Параметр `only`: `all` · `open` · `uncovered`. **«Открытое» у требования значит разное** — не
выполнено, не покрыто проверкой, не лежит в закрытой задаче, — и ручка обязана спрашивать,
какое из трёх, а не выбирать молча.

### `tasks-of(story)` и `stories-of(task)`
Два перехода: история → требование → задача. Цепочка держится: 231 пара история→задача на 184
истории. Четыре истории без требования — исключения из изменения 4, и ручка обязана называть
их исключениями, а не терять.

### `preflight-queue`
Задачи, которые пора прогнать в уме: незакрытые, с закрытыми зависимостями, у которых
предполёта не было либо он был до последней правки задачи. Второе требует, чтобы вердикт
хранился и знал ревизию, на которой получен. Сегодня вердикт не хранится нигде.

```sql
CREATE TABLE preflight_verdict (
  project_id text NOT NULL, task_id text NOT NULL, at bigint NOT NULL,
  task_revision bigint NOT NULL,
  verdict  text NOT NULL CHECK (verdict IN ('ready','ready-with-risks','blocked')),
  findings integer NOT NULL DEFAULT 0,
  body     text NOT NULL DEFAULT '',
  PRIMARY KEY (project_id, task_id, at)
);
```

Тогда «предполёт устарел» — сравнение ревизий, а не память.

### Что добавить в существующий `next-task`
Он уже снимает задачные и этапные блокировки. Не хватает трёх вещей:

- **барьера красной фазы.** Правило проекта: весь трек проверок предшествует всему коду.
  Сейчас `next-task` отдаёт `M0-T12` с `kind: dev`, не спросив, открыта ли красная фаза.
  Заметь: красных задач в `project_plan_tasks` **ноль** — вид `red-task` в раскладке помечен
  `due`, 82 документа и 492 пункта не разложены. Пока это так, барьер нечем проверить, и это
  первый пункт работы;
- **очереди с причиной** вместо одной задачи: почему эта первая и почему следующие не взяты.
  Одна задача без причины — совет, которому нечем возразить;
- **честного `requirementText`.** Сейчас нерастворимая связь печатается как `Q-277 · —`.
  Прочерк читается как «требование без текста»; на деле это не требование.

## Правила, которые держат это честным

**Зелёное, которое ни разу не роняли, не проверено.** Каждую новую проверку сломать нарочно и
увидеть красноту с именем, прежде чем объявлять её работающей.

**`unknown` — законное состояние, `done` по догадке — нет.**

**Вывод не хранится.** Всё выводимое живёт представлением.

**Объявленное отсутствие — факт со строкой.** Из объяснения отсутствия связи не добываются.

**Пустой ответ — факт, отсутствие объявления — дефект.**

**Не проектировать таблиц продукта.** База набора хранит то, что документ говорит, а не то,
что делает продукт. Признак ошибки: `session_id`, живые состояния, ключи на пользователей.
