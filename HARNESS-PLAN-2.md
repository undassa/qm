Добавочный промпт — работа в той же сессии, поверх уже сделанного. Проверено 2026-09-07 на
живой базе: из восьми пунктов приёмки первого плана проходят шесть.

**Проходят и трогать не надо:** `requirements-of` (отвечает фразой «нет собственных», а не
пустотой), `readiness` (все 1883 пункта перенесены, `declared` снят верно — 22 против 1861),
`claims` (`disagree: 1`, ровно статьи 15 против 16; ложные тревоги сняты полем `countsOver`),
`tasks-of` и `exceptions` (четыре исключения с причиной и `holeGone`), барьер красной фазы
(отказывает честно, называя причину), `gate('G5')` («отвечать нечем, и это не пройден»),
`preflight-queue` — я проверил обе стороны, подсадив вердикт и состарив ревизию; подсаженную
строку удалил.

Ниже — четыре незакрытых, по убыванию последствий.

## 1. Состояние задачи приходит из истории, а не из документа

**Это блокирует работу прямо сейчас:** `next-task` отдаёт `null` и будет отдавать всегда,
потому что барьер красной фазы не может узнать состояние 82 красных задач.

Разберись с причиной, а не с симптомом. Красная задача говорит о себе буквально:

> **Состояние не записано здесь намеренно.** Оно вычисляется из истории по закрывающему
> трейлеру `Task: R-M1-T1 closed`, **как у всех задач набора**: документ, несущий состояние,
> становится вторым источником истины и расходится молча.

А проекция делает обратное: `legacy-qm/src/projects/plan-projection.ts:94` — функция
`stateOf(field)` читает поле «Состояние» документа и достаёт коммит оттуда же. Обычные задачи
проецируются только потому, что их документы это поле несут, — то есть они и есть тот второй
источник истины, о котором предупреждает красная задача. Красные поля не несут (у них ровно
пять полей: «Фаза», «Этап родителя», «Родительская задача», «Проверок», «Какие»), и потому в
`project_plan_tasks` их ноль.

**Читатель трейлеров уже написан и не здесь.** Он в харнесе, у которого есть репозиторий:
`myack/.harness/scripts/lib/ids.mjs` держит единственный образец `Task: <задача> closed` — с
разобранными краями (`R-M1-T11a` против суффикса дробления `r`), — а `status.mjs` уже выводит
из него состояние и умеет сверять свой вывод с файлами. У сервера репозитория нет и не должно
быть.

**Значит: харнес подаёт, база принимает.** Ровно как `agents push`.

```sql
CREATE TABLE task_state (
  project_id text NOT NULL, task_id text NOT NULL,
  state text NOT NULL CHECK (state IN ('not_started','claimed','closed')),
  closing_commit text NOT NULL DEFAULT '',
  seen_at bigint NOT NULL,        -- когда харнес это видел
  PRIMARY KEY (project_id, task_id)
);
```

Тогда `project_plan_tasks.state` перестаёт быть фактом документа и становится выводом; поле
«Состояние» в документах задач подлежит снятию отдельным проходом по набору — но снимать его
в этой работе не надо, сперва должен появиться источник.

Красные задачи разложить в те же таблицы (`kind='red'`), с родительской задачей и списком
проверок из поля «Какие»; в раскладке снять `red-task: due`.

**Приёмка.** Красных задач в `project_plan_tasks` 82. `next-task` либо отдаёт задачу, либо
отказывает, **называя открытые красные задачи поимённо**, а не «состояние неизвестно». Задача,
чей трейлер есть в истории, а поле «Состояние» в документе говорит другое, видна отдельным
запросом как расхождение — это и есть тот второй источник истины, пойманный за руку.

## 3. Убрать путь из `readiness_item`

`owner_id` документных чек-листов хранит путь: `50-plan/v1/order.md`,
`40-proof/acceptance.md`, `00-frame/document-plan.md`, `40-proof/test-plan.md`. Это возвращает
`path` в базу идентификатором — ровно то, чего в наборе быть не должно.

У трёх из четырёх вид есть, и все три одиночки в раскладке: `acceptance`, `test-plan`,
`document-plan`. Адресовать ими: `owner_kind='acceptance'`, `owner_id=''` — у одиночки
идентификатора нет, его опознаёт вид.

`order.md` вида **не имеет вовсе** — 145 пунктов принадлежат документу, который набор не умеет
назвать. Два честных исхода: завести вид `order` в раскладке, либо признать, что доска волны —
не сущность набора, и её пункты в `readiness_item` не место. Выбрать и записать выбор; молча
оставить путь — не исход.

**Приёмка.** `SELECT count(*) FROM readiness_item WHERE owner_id LIKE '%/%'` даёт 0.

## 4. Первая волна способов проверки

Из 1883 пунктов способ есть у нуля: `readiness_state` целиком `unknown`. Перенос — это первый
шаг, и он сделан правильно; второй не начат, и потому **ни одна галочка системой ещё не
проверена**.

Начинать не с задач. Начинать там, где способ уже написан словами:

```
приёмка  40-proof/acceptance.md    37 пунктов
гейты    00-frame/document-plan.md 18 пунктов — 11 из них единственные отмеченные во всём наборе
```

Пункты гейтов вдобавок уже имеют рядом машинную родню: 13 строк `query` в `project_gates` с
готовыми запросами. Свести их — и станет видно, какие из 18 пунктов документа держатся
запросом, а какие только словом.

Два правила, без которых волна принесёт вред:

- **`unknown` остаётся `unknown`.** Пункт без объявленного способа не становится `done` ни от
  какого сопоставления слов. Зелёный чек-лист, который ничего не мерит, хуже отсутствующего:
  его читают и верят;
- **каждый новый вычисляемый пункт роняется нарочно один раз.** Зелёное, которое ни разу не
  падало, не проверено — в этом наборе так уже находились и гейт, меривший уже, чем обещал, и
  проверка, объявлявшая перенесённое лишним.

Заодно завести пункт гейта вида `command`: строк с ним ноль, хотя схема его допускает, а
`document-plan.md` полон дословных команд, которые прогоняет человек. Пункт хранит команду и
то, что считается успехом («пусто», «код 0», «= N»).

**Приёмка.** Вычисляемых пунктов больше нуля. Хотя бы у одного `declared` расходится с
вычисленным — на нарочно испорченном примере, и расхождение видно в `readiness`. `G5`
по-прежнему отвечает «пунктов нет», пока их не завели: отказ не заменяется зелёным.
